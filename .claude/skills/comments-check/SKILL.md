# 注释质量检查

对指定目录或文件进行注释质量检查，覆盖三个维度：

1. **完整性** — 函数和核心逻辑是否缺少注释
2. **一致性** — 注释内容是否与代码实际行为匹配
3. **可读性** — 注释是否适合初学者理解

## 触发方式

在任意代码检查场景中，当用户要求检查注释时使用本技能。如果未指定目录，默认扫描 `src/` 下的所有 `.ts`/`.tsx`/`.js`/`.jsx` 文件（排除 `node_modules` 和 `*.test.ts*` 测试文件）。

## 检查范围

根据项目实际代码风格，需要检查的文件类型：

| 类型 | 说明 |
|------|------|
| `src/**/*.ts` / `.tsx` | 主要业务逻辑文件 |
| `src/**/index.ts` | 模块入口文件 |
| `src/**/*.test.ts*` | 测试文件（可选检查） |

**排除范围：**
- `node_modules/`
- `dist/`
- `src-tauri/target/`
- 自动生成文件

## 检查维度一：注释完整性

### 必须注释的元素

以下元素必须拥有注释（JSDoc `/** ... */` 或行内 `//` 注释）：

1. **导出的函数 / 方法**
   - 每个 `export function` 必须有注释
   - 每个类方法（`public`/`private`）必须有注释
   - JSDoc 必须包含：功能描述、参数说明、返回值说明

2. **导出的常量 / 枚举**
   - 较大的常量对象（如 `SEED_CATEGORIES`）必须有注释说明其用途
   - 枚举类型必须有注释

3. **导出的接口 / 类型**
   - 接口和类型别名必须有注释，说明字段含义

4. **核心逻辑代码块**
   - 复杂条件判断（`if/else` 分支）必须注释意图
   - 算法/计算逻辑块必须注释思路
   - 数据转换/映射逻辑必须注释目的
   - 边界处理（`if` 判断空值、异常情况等）必须注释原因

5. **状态管理 / Store**
   - 每个 zustand store 的 action 必须注释
   - 状态变更逻辑必须注释目的

### 注释格式规范

**JSDoc 格式（推荐用于导出函数/类）：**

```typescript
/**
 * 函数功能一句话描述
 *
 * @param paramName 参数说明（类型、含义、是否可选）
 * @param anotherParam 另一个参数说明
 * @returns 返回值说明
 */
export async function doSomething(paramName: string): Promise<void> {
  // ...
}
```

**行内注释（用于代码块解释）：**

```typescript
// 解释这一行或这一段代码的目的
// 例如：过滤掉已删除的分类
const active = items.filter((item) => !item.deleted);
```

**禁止的注释格式：**

```typescript
// ❌ 无效注释：只是重复代码，没有信息量
const x = 1; // x等于1

// ❌ 无效注释：过于简短，没有说明意图
// 处理
handleData();

// ❌ 无效注释：英文缩写且含义不明
// TODO: refactor later
doComplexLogic();
```

**推荐的注释格式：**

```typescript
// ✅ 说明意图：为什么这么做
// 为旧分类补上 type 字段，兼容迁移前的数据
for (const c of categories) {
  if (!c.type) {
    await db.categories.update(c.id, { type: 'expense' });
  }
}
```

## 检查维度二：注释一致性

### 检查要点

1. **注释描述的功能与实际代码行为一致**
   - 注释说"获取所有交易"，但代码只过滤了未删除的 → 不一致
   - 注释说"支持两种格式"，但代码只处理了一种 → 不一致

2. **参数描述与实际签名一致**
   - 注释说接受 `name` 参数，但函数签名是 `title` → 不一致
   - 注释说返回值是 `string`，但实际返回 `string | null` → 不一致

3. **注释中的示例与实际逻辑匹配**
   - 注释举例说明行为，但举例不符合实际执行路径 → 不一致

4. **过时注释**
   - 代码已修改，但注释仍描述旧行为 → 过时

### 常见不一致示例

```typescript
/**
 * 获取所有收入记录
 */
export async function getExpenses(...): Promise<Transaction[]> {
  // 注释说"收入"，但函数名是"支出"，实际代码也过滤了 expense
  // → 注释与函数名/行为不一致
}
```

## 检查维度三：注释可读性（初学者友好）

### 判断标准

注释对初学者是否友好，检查以下方面：

1. **术语是否解释**
   - 出现专业术语（如 `Dexie`、`zustand`、`IndexedDB`）时，注释应简要说明其作用
   - 出现业务缩写时（如 `UUID`、`ISO`、`BOM`），应有说明

2. **逻辑是否解释清楚**
   - 复杂逻辑块（多步骤处理、条件分支）应注释每一步的目的
   - 避免只注释"做了什么"，要注释"为什么这么做"

3. **语言是否自然**
   - 避免中英文混杂且无解释（如直接写 "handle error" 而不解释）
   - 避免纯英文注释（项目主要面向中文用户，注释应使用中文）

4. **上下文是否充足**
   - 注释应提供足够的上下文，让初学者不需要查源码也能理解
   - 对于数据迁移、兼容性处理等，应解释背景原因

### 初学者友好注释示例

```typescript
// ✅ 好的注释：解释背景 + 意图
// 从 expenses 迁移到 transactions
// v2: 将旧表数据迁移到新表，并补充 type 字段
this.version(2).stores({...}).upgrade(async () => {
  // ...
});

// ❌ 不好的注释：只有代码动作，无上下文
// 迁移
this.version(2).upgrade(async () => {
  // ...
});
```

## 执行步骤

### Step 1：发现文件

```bash
find <target_dir> -type f \( -name "*.ts" -o -name "*.tsx" -o -name "*.js" -o -name "*.jsx" \) \
  | grep -v "node_modules" \
  | grep -v "dist/" \
  | grep -v ".test.ts" \
  | grep -v "target/" \
  | sort
```

### Step 2：逐文件分析

对每个源文件执行以下检查：

1. **识别所有导出函数/方法** → 检查是否有注释
2. **识别所有接口/类型定义** → 检查是否有注释
3. **识别核心逻辑块**（复杂条件、循环、映射、数据转换）→ 检查是否有注释
4. **核对注释内容与代码行为是否一致**
5. **评估注释的初学者友好程度**

使用以下格式输出检查结果：

## 特殊场景处理

### 测试文件（`*.test.ts` / `*.spec.ts`）
- 测试用例标题（`it` / `test` / `describe`）通常不需要额外注释
- 测试中的关键断言可以添加简短注释说明验证意图

### 自动生成文件
- `vite-env.d.ts`、`*.generated.ts` 等由工具生成的文件跳过检查

### 纯类型声明文件（`.d.ts`）
- 类型声明的注释要求可以适当放宽

### 单行简单代码
- `const x = 1;` 这类一行简单赋值不需要注释
- 判断标准：如果代码本身一目了然，可省略行内注释

## 输出建议

检查完成后，按以下顺序给出建议：

1. **高优先级**：列出所有缺失注释的函数/代码块，并给出建议的注释内容（JSDoc 格式）
2. **中优先级**：列出所有不一致的注释，给出修正建议
3. **低优先级**：列出可读性不足的注释，给出优化建议

如果问题较多（超过 20 个），优先列出前 10 个最严重的问题，然后建议用户分批次修复。
